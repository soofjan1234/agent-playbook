# 技术结论翻译与汇报

把已经调查或验证过的技术事实，转成读者能据此判断和行动的说明。它不替代排障、实现、审查或验收 skill；应与当前工程阶段一起使用。

## 适用时机

- 用户说“解释一下”“总结”“结论”“汇报”“给上级看”“说人话”或表示没有看懂技术结果。
- 当前任务出现了会改变结论、范围、风险或下一步的实质性问题。
- 问题已定位或修复，或任务已有经过验证的阶段性或最终结果。

不为普通进度、未验证猜测或无实质变化的工具输出额外生成汇报。

## 写法

先给一到两句非技术结论，再按读者需要补充最少的依据。默认避免缩写、内部组件名、日志原文和命令；必须使用时，在首次出现处说明其用途。

根据所处阶段选择内容：

| 阶段 | 必须回答 |
| --- | --- |
| 问题出现 | 发生了什么、实际影响、已排除什么、下一步如何确认或处理 |
| 问题解决 | 根因、采取的改动、验证证据、剩余风险或限制 |
| 任务完成 | 目标是否达成、关键验证、未覆盖范围、建议的下一步 |

## 事实边界

- 明确区分已验证事实、合理推断和未知项；不要把推断写成结论。
- 功能验证、性能测试和稳定性验证是不同结论。一次成功运行只能证明对应功能路径可用。
- 只有当前回合的证据支持时，才能说“已解决”“已通过”或“已完成”。
- 不因汇报需要而增加外部操作、扩大任务范围，或掩盖失败和限制。

## 输出强度

- 用户只要一句结论时：给结论和一个最重要的边界。
- 面向执行者时：补充原因、影响和下一步。
- 面向上级时：用一段可直接转发的话说明结果、业务影响和是否还需要决策；技术明细仅在有助于追问时保留。

若用户未指定对象，先按“理解当前工作的执行者”来写；只有当受众会实质影响结论或措辞时才询问。
