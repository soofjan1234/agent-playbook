# 工程评审

以明确的评审对象、比较基准、需求和当前事实为依据，发现错误、遗漏及可简化或优化之处。

## 核心关卡

1. 明确评审对象、范围、基准、目标和原始需求；缺失时先调查，无法确认的内容标记为限制。
2. 判断评审模式，只读取当前模式需要的 reference；混合产物按“设计 → 计划 → 代码变更”的依赖顺序分别评审。
3. 区分已验证事实、合理推断和待决策事项，不把偏好包装成缺陷。
4. 依次检查错误、遗漏、可简化项和可优化项；正确性与必要约束优先于优化。
5. 每个问题都提供严重度、类别、证据、影响、具体位置、可执行建议和验证方式。
6. 阻断问题解决前不得给出批准、执行或合并建议；没有可执行问题时明确说明，并列出未覆盖的事实和残余风险。
7. 评审只授权调查和报告，不授权修改产物；用户明确要求修复后再进入对应实现流程。

## 模式路由

| 评审对象 | 使用方式 |
| --- | --- |
| branch、PR、commit、workspace diff 或代码合并就绪性 | 读取 [代码变更评审](references/code-review.md) |
| 设计文档、技术方案、接口契约、流程、观测或集成方案 | 读取 [设计评审](references/design-review.md) |
| 实施计划、任务拆解、迁移步骤、测试或发布计划 | 读取 [计划评审](references/plan-review.md) |

同一文档同时包含多类内容时，只加载实际存在的模式，不机械执行所有检查。设计尚未成立时，计划的精细程度不能抵消上游问题；计划尚未形成可执行路径时，代码完成度也不能证明整体方案正确。

## 发现类别

1. **错误**：与事实、需求、约束或内部逻辑冲突，可能导致错误结果或不可执行。
2. **遗漏**：缺少完成目标所必需的场景、边界、契约、风险或验证。
3. **简化**：能够删除不必要的层次、状态、分支、任务或重复机制，同时保持目标与约束。
4. **优化**：在方案已经正确且完整的前提下，改善边界、顺序、可维护性、性能或验证效率。

简化和优化必须说明收益、代价及适用条件；没有明确收益的个人风格偏好不作为发现。

## 严重度与输出

- **阻断**：目标无法达成、关键事实错误、存在重大安全或兼容风险，或产物不可执行。
- **重要**：不会立即阻断，但很可能造成回归、返工、歧义或验证缺口。
- **建议**：有证据支持的简化或优化，不影响当前产物成立。

先按严重度列出问题，再给总体结论和残余风险。每个问题使用最窄的文件、章节、任务、符号或行号定位；不要写无法定位、无法验证或无法执行的泛化建议。

## 处理外部审查意见

1. 先读完全部反馈，按对应评审模式核对原始产物和事实。
2. 对含糊意见提出精确问题，不做表演式认同。
3. 判断意见成立、部分成立、需要补证还是应拒绝，并说明证据。
4. 技术上错误、越界或不安全的意见应明确拒绝。
5. 只有用户明确要求修改时，才把接受的意见交给相应实现流程并验证。

## 红旗

- 没有基准、需求或当前事实就声称完成评审。
- 对设计或计划机械运行代码质量、文件行数或 race 检查。
- 用工具分数、文档完整度或任务数量代替真实可行性判断。
- 只检查格式和风格，遗漏行为、边界、风险和验证。
- 把可选优化写成阻断问题，或为展示深度制造无收益的复杂建议。
- 接到评审请求后直接修改代码、设计或计划。
