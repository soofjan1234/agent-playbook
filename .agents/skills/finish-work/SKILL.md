# 验证与收尾

用当前证据完成工作，并让分支和上下文都有明确去向。

<HARD-GATE>
完成、修复、构建和测试结论必须符合 [公共执行与证据规则](../SKILL.md#公共执行与证据规则)。证据不匹配当前产物、输入或环境时，不得据此声称通过。
</HARD-GATE>

## 按变更类型选择验证

验证强度应与变更风险和实际影响匹配。

- 仅修改说明性 Markdown、注释或交接文档，且不影响代码、配置、生成物或接口契约时，不运行无关的代码测试、构建或部署验收；检查实际差异、内容完整性、状态一致性和相关链接即可。
- 文档同时定义配置、接口契约、生成流程或可执行命令时，验证受影响的契约或命令。
- 验证证据不等同于必须执行测试；文档、差异和契约核对也可支持相应结论。

## 验证关卡

1. 为每项结论确定能证明它的命令或检查。
2. 检查可复用证据是否匹配当前产物、输入和环境；需要重跑时执行完整且相关的验证，读取退出码、失败数和关键输出。复用时注明原验证时间，不冒充本次运行。
3. 失败时报告实际失败，不用“基本完成”弱化结果。
4. 成功时同时说明执行了什么和证据是什么。
5. 若当前计划已登记主题计划表：补充完成结果与证据摘要，全部必需验证通过后更新为 `已完成`；当前环境可运行的自动验证通过但仍缺外部或人工验证时更新为 `待验证`；验证失败或实现未就绪时保持或退回 `待实现`。具体规则见 [状态账本规范](../references/status-ledger.md)。
6. 按 [文档管理规则](../references/documentation-policy.md) 更新受影响的权威正文，执行其中的删减检查：清理重复与失效内容，保留必要契约和证据，核对状态、入口与链接；无需更新时说明原因。
7. 分开核对阶段通过条件和整体验收标准。验收记录保存实际结果与证据，不创建第二套标准。

| 结论 | 必需证据 |
| --- | --- |
| 测试通过 | 测试命令退出码为 0，且确认无失败 |
| 构建成功 | 构建命令退出码为 0 |
| Bug 已修复 | 原始症状或回归测试通过 |
| 需求完成 | 逐项核对需求与变更 |
| agent 已完成 | 独立检查实际差异和输出 |

## 完成汇报

结束汇报先帮助用户做判断，再补充工程执行细节。默认按以下顺序组织：

1. 用一两句话说明业务结论，以及结果对用户意味着什么。
2. 说明结论采用的评价前提或成功标准；测试结果依赖数据规模时，同时说明测试对象和规模。
3. 给出影响决策的核心数据，避免用 `passed`、`rejected` 等内部状态代替自然语言结论。
4. 分开说明已验证事实、合理推断和未验证范围；一次冒烟、功能验证或单轮测试不得表述成完整性能或稳定性结论。
5. 最后再列测试命令、文件链接、Git 状态和其他工程细节。

如果不同目标会产生不同结论，例如节省内存但增加磁盘占用，应分别给出条件化结论，不得擅自选择评价标准或把用户未要求的指标设为硬门槛。若缺少决定性指标，应明确说明当前能判断什么、不能判断什么，以及补齐结论所需的最小验证。


## 分支收尾

验证通过后，按用户已授权的收尾目标执行；已要求推送并创建 PR 时直接完成，不重复提供菜单。未要求 Git 操作时保持工作区，只在确有未决定事项时提供相关选择。

保护用户未提交工作；丢弃、删除和其他破坏性操作仍需明确确认。只清理由当前流程创建且确认安全的 worktree；创建 PR 后保留工作区以便继续审查。

## 会话移交

需要新会话继续时，生成精简移交文档，包含目标、当前状态、未完成事项、验证证据和建议调用的 skill。已有规格、计划、ADR、Issue、提交和差异只引用路径或链接，不重复复制。

创建或更新交接文档时，按 [状态账本规范](../references/status-ledger.md) 同步主题中已有设计表和计划表；计划表更新真实状态、完成结果、下一步和日期。只有交接或范围说明时，在主题说明中记录下一步，不虚构设计或计划文件。交接文档写完不代表计划完成。

## 红旗

- 引用与当前产物、输入或环境不匹配的旧测试结果，或把复用结果冒充本次运行。
- 用 lint 结果代替构建或测试结果。
- 未经确认删除分支、worktree 或用户工作。
- 移交文档复制大量已经存在的内容。
