# 防御工作流地图页面契约

地图以已确认的 `plan.md` 为起点。计划阶段先记录应测场景；实现后才以真实运行结果更新状态。页面只展示“做了什么”“应测场景”“可能漏掉什么”；源码与测试只用于内部取证。

```text
feature
  name: 功能名称
  scope: 所分析的 diff、提交或文件范围
  evidence: 使用的入口和关键源码位置，仅内部取证使用

nodes[]
  id: 稳定标识
  step: 展示顺序
  title: 节点名称
  responsibility: 节点职责的短标题
  plainExplanation: 面向读者的人话解释
  oneSentenceSummary: 一句话说明节点的业务作用
  concreteWalkthrough: 一个最小业务例子，展示前置状态、动作和结果
  keyTerms[]: 当前节点中 1～3 个必要术语及其人话定义
  commonMisconception: 最可能的错误理解及其边界
  preconditions: 前置条件
  success: 成功后可观察的结果
  sourceRefs[]: 路径和行号，仅内部取证使用
  expectedScenarios[]: 此节点应被验证的场景
  likelyGaps[]: 未充分证明的高风险缺口

plainExplanation
  problem: 这一步解决什么问题
  context: 谁在什么情况下触发它
  handling: 系统按什么判断和动作处理，按因果顺序表达
  outcome: 成功、拒绝或失败时可观察的结果
  importance: 这一步保护什么业务规则或避免什么后果

expectedScenarios[]
  id: 稳定标识
  title: 场景名称
  kind: normal、exception、recovery、boundary、idempotency、concurrency 或其他适用类别
  trigger: 输入、状态或触发条件
  expectedOutcome: 应被证明的可观察结果
  rationale: 由哪个行为分支、副作用或契约推导
  status: pending、proven、partial 或 needs-confirmation
  statusReason: 状态的证据边界
  evidenceTestIds[]: 仅 proven 或 partial 时关联的内部测试 ID
  sourceRefs[]: 路径和行号，仅内部取证使用

likelyGaps[]
  scenarioId: 对应 expectedScenarios 的 ID
  risk: 可能漏掉的行为或条件
  consequence: 若发生会造成的后果
  rationale: 为什么现有证据不足

tests[]
  id: 稳定标识
  name: 测试名称或参数化用例名
  file: 相对仓库路径
  line: 可定位行号
  how: 测试如何构造输入、执行什么动作
  proves: 关键断言最终证明的可观察行为
  assertions[]: 关键断言
  relation: 与节点或场景的关联理由
  confidence: confirmed 或 needs-confirmation
```

## 解释规则

- `plainExplanation` 默认由 3～5 句自然语言组成，按“问题 → 场景 → 处理 → 结果 → 意义”表达；字段可合并为一句，但五层信息不能被代码细节替代。
- 使用业务动作和可观察结果，例如“拒绝取消并保持库存不变”，不要写函数名、包名、字段名、源码行或“先调用 A 再调用 B”。
- `importance` 必须能从实际业务规则、状态约束或副作用推导；不能为了显得完整而编造价值判断。
- 若节点没有拒绝/失败分支，`outcome` 如实只写成功结果，并在应测场景中说明该限制。

## 节点教学字段

### `oneSentenceSummary`

- 用一句自然语言说明节点在完整业务链路中的职责，不能仅重复节点标题。

### `concreteWalkthrough`

- 使用最小虚构角色和业务对象，按“进入时状态 → 人或系统动作 → 最终状态/可观察结果”叙述。
- 例子必须与当前计划、实现和测试证据一致；它用于解释，不是额外承诺或测试证据。
- 节点涉及多轮邮件、版本、审核、归档或重试时，例子必须点出本节点实际改变的对象，不能只说“系统处理完成”。

### `keyTerms[]`

- 每项含 `term` 与 `meaning`；只列理解本节点必需且容易混淆的术语，通常 1～3 项。
- 不解释函数、类、包、数据库字段等实现标识，除非它本身就是用户可见的业务术语。

### `commonMisconception`

- 用“不要误解：……”表达一个本节点能防止的错误推断，例如“已审核不等于已发布”。
- 必须说明当前边界，不得编造尚未实现的恢复、权限、性能或自动化能力。

## 状态规则

- `pending`：计划阶段默认状态，显示为 `○ 待验证`。
- `proven`：显示为 `✓ 已证明`；仅当测试真实运行通过，且关键断言直接证明该场景预期结果时可使用。
- `partial`：显示为 `△ 部分证明`；测试覆盖相似路径，但关键触发、状态变化或副作用没有被直接断言。
- `needs-confirmation`：显示为 `? 待确认`；测试未运行、未提供、无法解析或无法可靠关联。

异常结束与恢复必须参与场景推导，但不作为独立视觉区域。正常分支、异常分支和恢复分支都应转化为明确的 `expectedScenarios[]`；仅未充分证明的场景才能产生 `likelyGaps[]`。

## 展示规则

- 页面从 `assets/feature-defense-map.html` 生成，保留其渐变页头、紧凑/展开流程、四格节点讲解和三列防御信息；只替换元数据与节点数据。
- 页面上方是功能地图。默认是一行紧凑导航，只显示步骤和短标题；提供展开/缩回切换。展开状态可显示职责，测试数量和风险不作为节点徽标。
- 点击节点后，只展示“做了什么”“应测场景”“可能漏掉什么”三块内容。
- “做了什么”以 `oneSentenceSummary`、`concreteWalkthrough`、`keyTerms[]`、`commonMisconception` 与 `plainExplanation` 为内容来源。固定显示“一句话结论、举个例子、关键术语、不要误解”；需要时再以“发生场景、系统处理、结果与意义”补足，不要展示实现标识符。
- 每个场景内联展示状态及状态原因；不得设置独立的覆盖判断板块。
- 页面不得展示源码片段、测试名称、文件位置、测试动作、断言、关联理由或“查看依据”入口。它们保留在内部数据中，仅当用户在对话中明确要求定位时提供。
- 计划阶段没有测试时仍展示应测场景并标 `pending`；实现后没有真实运行或直接断言时标 `needs-confirmation`，不要把无测试隐藏成无风险。
- 页面支持键盘操作、可见的选中状态和窄屏纵向排版。
- 页面固定使用浅色方案。不得添加随系统深色模式覆盖全局文字变量的样式；状态选择器必须限定在场景区域，不能影响页头说明。
- 主要文字及状态颜色与其背景的对比度不得低于 `4.5:1`。

## 验收

1. 所有主流程节点都有 `plainExplanation`、至少一个源码证据或明确的待确认标识。
2. 每份 `plainExplanation` 包含问题、场景、处理、结果和意义，并且没有把代码标识符/调用顺序作为正文。
3. 每个节点均有 `oneSentenceSummary`、`concreteWalkthrough`、1～3 个 `keyTerms[]` 与 `commonMisconception`；例子能说明输入或前置状态、动作和可观察结果。
4. 每个节点的应测场景都说明触发条件、预期结果、推导原因和当前状态。
5. 每个 `✓ 已证明` 都有本次真实运行和直接断言的内部证据；其余场景不得打勾。
6. 异常/恢复行为已融入相应场景，页面没有独立异常区或覆盖判断板块。
7. 页面没有关键代码区、测试清单或“查看依据”入口。
8. 至少验证一次 `✓ 已证明` 场景和一次 `△ 部分证明`、`○ 待验证` 或 `? 待确认` 场景的点击切换。
9. 默认紧凑导航、展开流程及缩回导航均可用；切换不应丢失当前选中节点。
10. 若分析受限于未确认计划、未提供 diff、无法运行测试或测试名称无法解析，页面和交付说明必须如实标注边界。
11. 在实际渲染页面中检查页头、节点选中态、四格讲解、三列防御信息、展开/缩回及窄屏布局；语法检查不能替代视觉检查。
12. 主要正文、次要文字、状态、强调标题和警示标题均满足至少 `4.5:1` 的颜色对比度，且系统深色模式不会造成浅色卡片上的文字不可读。
