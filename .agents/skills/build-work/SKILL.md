# 测试驱动实现

按明确需求或计划，以最短反馈循环交付可验证的纵向行为。

## 核心关卡

1. 先完整理解已确认范围、系统设计或计划；范围与验收歧义退回 shape-work，架构与契约歧义退回 design-work，执行步骤歧义退回 plan-work。
2. 检查分支和工作区是否安全；需要隔离时优先使用平台原生能力，再考虑 Git worktree。
3. 每个行为执行 RED → GREEN → REFACTOR：先看到测试按预期失败，再写最小实现。
4. 定期运行目标测试和类型检查，全部完成后运行相关完整验证。
5. 只有任务独立、不会修改相同状态时才并行；否则按依赖顺序执行。
6. 若当前工作项已登记状态账本，实现期间保持 `待实现`；实现完成且当前环境可运行的自动验证通过、只剩外部或人工验证时改为 `待验证`。具体规则见 [状态账本规范](../references/status-ledger.md)。

## 实现循环

1. 选择下一个最小用户可观察行为。
2. 编写一个聚焦于公共行为的测试。
3. 运行测试并确认失败原因正确；测试立即通过时先修正测试。
4. 编写使它通过的最小生产代码。
5. 运行目标测试和相邻测试。
6. 在保持绿色的前提下重构。
7. 继续下一个行为。

实现中发现契约变化或新的长期限制时，先处理必要的设计确认，再更新对应权威正文。文档写回遵循 [文档管理规则](../references/documentation-policy.md)，不把变更历史复制成第二份当前说明。

测试应一例一行为，名称表达业务预期，尽量使用真实代码，只模拟不可避免的边界。测试难写通常意味着接口或接缝需要简化。

## 中文注释规范

以下规则只约束本次新增或修改的代码，不为补注释而批量改动无关旧代码：

- 为具有业务含义、单位、边界、协议值或不直观用途的常量定义添加中文注释；语义已经由名称完整表达的普通常量不强制注释。
- 为存在依赖关系、执行顺序、默认值、降级行为或环境约束的初始化逻辑添加中文注释，说明为什么这样初始化。
- 新增或修改的具名函数和方法统一使用中文文档注释说明用途、职责、关键约束或副作用，并遵循对应语言的文档注释格式。
- 函数包含多个明显业务步骤时，使用 `// 1.`、`// 2.`、`// 3.` 按实际执行顺序标注关键步骤。步骤注释必须独占一行并位于对应代码之前，不得写在代码行尾。
- 为复杂业务逻辑和核心算法说明业务意图、关键不变量、边界条件或选型原因；不要逐行翻译代码。
- 简单赋值、直观判断、普通调用、getter、setter 等语义明确的代码不添加无意义注释。
- 注释与代码同步更新；注释重点解释用途和原因，不重复变量名、函数名或语句表面含义。

## 执行模式

- **单 agent**：小型任务或共享状态较多。
- **顺序子任务**：计划包含多个相对独立切片；每项完成后审查再继续。
- **并行调查或实现**：仅限完全独立的问题域和文件范围，合并后统一验证。

使用子 agent 前遵守平台能力和用户授权，不为追求形式而拆分任务。

## 红旗

- 生产代码先于失败测试，且用户没有明确允许例外。
- 测试失败原因不明仍继续实现。
- 用大量 mock 验证实现细节。
- 多个 agent 同时编辑同一文件或共享状态。
- 目标测试通过后跳过构建、类型或相关回归验证。
- 为追求注释数量逐行复述代码，或给未修改旧代码做无关的批量注释改造。
- 将编号步骤写在代码行尾，或让编号顺序与实际执行顺序不一致。
