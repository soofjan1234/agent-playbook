# Markdown 文档写作

从读者需要理解的事情组织正文。简洁不只看篇幅：读者应能直接理解谁做什么、事情怎样发生，以及哪些条件会改变结果。用户指定的内容、格式和项目约定优先。

## 写入前

- 明确读者、用途和要支持的判断；可从任务推断时不额外追问。工程文档默认读者了解项目用途，但未读过相关源码，不默认其熟悉实现术语。
- 先读目标文档和必要的相邻材料，沿用已有组织，避免建立平行正文。
- 工程文档遵循现有[文档管理规则](../references/documentation-policy.md)，职责、组织和状态不在这里重复维护。当前会话已读且规则未变时无需重读。

## 写作与改写

- 正文只保留读者完成本文对应的判断或操作需要的信息，不因“以后可能用到”展开细节。设计检查项用于查漏，不要求逐项写成章节。
- 开头直接回答读者最关心的问题。解释设计或流程时，先用一个相关场景讲清运行过程，再介绍模块、接口和限制；内容本身已清楚时无需补例子。
- 句子尽量写成“谁，在什么情况下，做什么，结果怎样”。检查“收敛、边界、契约、冻结”等抽象表达能否换成具体动作，不把它们当禁词。例如“管理和模型准备独立收敛”改为“调度器先启动，再准备模型和启动管理接口”。
- 必要术语首次出现时用一句话或括号解释，保留准确的代码和接口名称。不要用未解释的新术语解释另一个术语。
- 一段回答一个问题；包含不同条件、多个动作或例外时拆开。表格用于比较，列表用于步骤或并列事项，不为缩短篇幅把多个问题挤进一个单元格。
- 正文先讲清方案，再放影响本次决定的技术细节。逐文件任务和执行顺序留给实施计划；已有专项材料用链接，不为缩短正文另建没有独立用途的文档。
- 删除重复背景、空泛总结和无关展开。同一规则在正文中只解释一次；验收只写可观察的通过条件，不重新讲解方案。跨文档的同一事实只在权威正文维护，其他位置引用。
- 保留必要的数值、统计分母、失败行为、兼容条件、验证标准和依据。区分当前事实、拟议方案与未验证结论，不为追求短篇幅改变原意。
- 控制阶段：需求说明目标与范围；设计说明运行方式、关键取舍和验收；计划说明实施步骤与验证。组织随内容和用户要求调整，不强制章节数、字数或模板。

## 写后检查

实际阅读写入后的正文，先删无关内容、合并重复，再精简句子；不把压缩字数当作易懂的证明：

1. 不读源码，能否说清本文解决什么问题、事情怎样做、还有哪些条件或待决定事项？设计文档尤其要能回答“改什么、修改后怎样运行、还没决定什么”。不能回答就重写对应段落。
2. 有没有需要读者自己翻译的抽象句、未解释术语，或同时讲多个问题的段落？换成具体动作、补解释或拆段。
3. 删除某段是否影响读者完成本文对应的判断或操作？不影响就删；已有正文能解释的内容用链接，不以其他阶段或未来用途为保留理由。
4. 核对精简前后的关键决定、数值、原因、失败处理和验收要求，确认没有遗漏或改变语义；不能靠删掉必要条件使文档变短。

## 对照案例

设计文档难以判断详略，或用户反馈冗长时，依次阅读[错误案例](references/design-bad.md)和[正确案例](references/design-good.md)。两篇使用同一组业务约束，展示整篇内容取舍；错误案例只用于识别问题。学习删改理由，不照搬场景、参数或章节结构，其他任务无需加载。

检查实际差异和相关链接即可；普通说明文档修改不运行无关代码测试。本 skill 不授权额外写入，不新增审批，也不替代阶段 skill 的确认关卡。
