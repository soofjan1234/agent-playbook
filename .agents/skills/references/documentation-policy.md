# 文档管理规则

## 基本原则

- 每份正文回答一个主要问题。总体设计帮助读者理解核心流程与取舍；API、数据等专项文档按接口或实体提供可查阅的实现细节。
- 开头先写结论和适用范围；使用具体行为解释术语，删除重复背景、空泛总结和无关扩展。
- 同一事实只在一个权威正文维护，其他位置写摘要和链接。拆出的文档必须能从上级入口找到。
- 按阅读目的和独立维护需要拆分，不按固定行数拆分；没有独立内容时不创建空文件。

阅读软目标：总体设计争取 3 分钟理解核心流程与取舍，专项文档开头 30 秒内可定位结论。篇幅随必要内容调整，不为达标删减关键约束或机械拆出更多文件。

## 更新纪律

- 在原位合并、替换和删减，不把每次讨论追加成新段落。旧决策、失效方案和已解决待办退出当前正文；有追溯价值的内容保留在已有变更或验证记录中，并标明历史适用范围。
- 正文保留当前结论、必要理由和约束；请求 ID、哈希、逐次指标等详细证据留在对应记录或制品，以链接引用。通用限制与未验证边界集中说明，避免在多个章节反复补充。
- 交付前逐段检查：删去是否影响理解、决策、实现或验证？不影响则删除或合并。保留必要输入输出、错误语义和验收条件，不以字数作为完成标准。

## 工作阶段与产物

| 阶段 | 回答的问题 | 主要内容 |
| --- | --- | --- |
| 需求对齐 | 为什么做、做什么、哪些不做、何时算成功 | 目标、范围、非目标、约束、大致交付阶段、整体验收标准 |
| 系统设计 | 系统如何实现 | 架构、数据模型、状态流、接口契约、失败恢复和关键取舍 |
| 实施计划 | 具体如何执行和验证 | 修改文件、关键函数、执行顺序、测试方法和通过条件 |

下游材料引用上游结论，不重新维护同一套范围和验收标准。范围变化回到需求对齐阶段；系统设计未决定的内容不能留给实施计划暗中补全。

## 文档组织

- MVP 资料放在 `docs/mvp/` 同一入口下。总体设计 `design.md` 放在目录外层；技术选型、API 设计、数据设计按需要拆成独立正文，统一放在 `architecture/` 子目录，并从总体设计及入口链接。计划和 `status.md` 保留在主题目录外层，不放进 `architecture/`。
- 小计划保留一份；复杂计划按可独立验证的交付阶段拆成总计划和子计划。
- 后续功能和复杂修复按主题保存在 `docs/changes/YYYY-MM-DD-<主题>/`，采用同样布局：总体设计在主题目录外层，技术选型、API 设计、数据设计在该主题的 `architecture/` 下。日期是主题首次创建日，后续更新复用同一目录，不因跨月新建平行主题。版本文档只汇总主题及整体验收，不复制设计与计划。
- 简单修复可在已有 Issue、提交或工作记录中保留原因、修复和验证，不强制创建完整文档组。

## 收尾

- 将已交付行为同步到当前架构、API、数据或操作说明；变更材料保留原因、方案和验证证据。
- 明确区分已批准、代码已实现、本地验证和目标环境验收。
- 每个主题的进度集中在一个 `status.md`，分为设计表和计划表，表内使用文档名而非链接；字段见 [状态账本规范](status-ledger.md)。MVP 与每个带日期的 changes 主题分别维护，顶层仅做导航；项目已有 Issue 或账本约定时优先遵循。
- 交接只写当前位置、阻塞、下一步和证据链接，不复制已有设计与计划。
