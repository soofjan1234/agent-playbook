# 代码变更评审

审查真实差异，而不是会话印象。先固定基准点、目标点、原始需求和仓库规范，再沿调用链验证行为。

## 评审步骤

1. 确认真正的 diff、未跟踪文件和评审范围，避免把基准外改动归入结论。
2. 分别检查需求符合性与工程质量，避免一个维度遮蔽另一个。
3. 当范围包含源代码时，对最小相关子目录运行 `fuck-u-code analyze <path> -l zh`；前后端分离时分别扫描。
4. 检查所有新增和修改源文件的行数，对超长文件执行职责与边界专项审查。
5. 检查新增和修改代码是否遵守 `build-work` 的中文注释规范。
6. 根据风险运行最具体的测试、静态检查、构建或并发验证；环境缺口必须作为残余风险报告。

## 六个维度

1. **需求**：是否完整实现规格，是否出现范围漂移。
2. **正确性**：边界条件、错误处理、并发、状态和兼容性。
3. **规范**：是否符合仓库文档和语言约定。
4. **设计**：模块边界、接口深度、耦合与可维护性。
5. **测试**：是否覆盖公共行为，是否存在无效或过度模拟的测试。
6. **规模**：新增和修改文件是否过长，是否混合多个职责，是否应拆出稳定边界。

## 质量与文件规模扫描

1. 对最小相关目录运行 `fuck-u-code analyze <path> -l zh`；大型仓库需要更多热点时使用 `-t <n>`，不要默认扫描无关目录。
2. 将总分、异常指标和热点文件作为风险地图，再回到真实差异和调用链验证；工具报告不能单独证明缺陷。
3. 工具不可用或执行失败时继续人工审查，并在结论中说明原因和缺失的质量证据。
4. 统计所有新增和修改源文件的总行数。默认超过 500 行时触发专项检查，但行数本身不构成问题。
5. 结合职责数量、嵌套和认知复杂度、修改频率、热点排名、相邻文件规模判断是否过长；新增超长文件从严审查。
6. 生成文件、第三方依赖、快照和纯数据文件不参与长度判断。
7. 发现超长文件问题时，指出应拆出的具体职责、边界和验证方式，不只写“文件太长”。

审查结果应简述 `fuck-u-code` 的关键证据，列出触发专项检查的文件及判断；未执行扫描时明确残余风险。

## 注释审查

1. 只审查本次新增或修改范围，不要求为无关旧代码批量补注释。
2. 检查重要常量和初始化逻辑是否说明业务含义与原因，具名函数和方法是否使用符合语言约定的中文文档注释。
3. 多步骤业务函数应使用独占一行的 `// 1.`、`// 2.`、`// 3.` 按执行顺序标注，且注释放在对应代码之前，不能写在代码行尾。
4. 复杂业务和核心算法应解释业务意图、关键不变量、边界条件或选型原因；简单代码不得用复述实现的注释制造噪音。
5. 仅当缺失、错误或过时注释会影响理解和维护时提出问题，并指出应补充的具体意图或约束。

## Go 并发验证

当差异涉及共享状态、锁、goroutine、客户端热切换或其他并发行为时，优先对最小相关包运行 `go test -race`，不要求无关审查默认执行全仓 race 检测。

Windows 下若 `CGO_ENABLED=0`，可在当前 PowerShell 命令会话临时启用：

```powershell
$env:CGO_ENABLED = '1'
go test -race ./相关包/...
```

`-race` 还需要当前平台支持且存在可用的 C 编译器。环境不满足时继续代码与同步关系审查，在结论中明确 race 检测未覆盖及原因；不得把环境失败视为代码测试失败。

## 代码评审红旗

- 没有基准点就声称审查了全部变化。
- 只检查风格，不检查规格、行为和调用链。
- 用 `fuck-u-code` 分数代替对真实差异的审查。
- 仅凭超过行数阈值就要求拆分文件。
- 为简单代码缺少注释提出形式化问题，却遗漏复杂业务和核心算法的关键解释。
- 把静态检查、编译证明或环境失败误报为测试通过。
