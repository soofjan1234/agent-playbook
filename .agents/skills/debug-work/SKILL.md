# 系统化排障

先证明根因，再实施修复。

<HARD-GATE>
没有完成根因调查前，不得提出或实施猜测性修复。
</HARD-GATE>

## 核心关卡

1. 稳定复现问题，或收集足以精确描述失败的证据。
2. 阅读完整错误、堆栈、日志和实际行为。
3. 优先用明确函数名、事件名、测试名定位核心文件，并对比一个相邻正常路径。
4. 从错误状态向上游追踪来源，形成一个可证伪假设。
5. 用最小探针验证这一假设；一次只改变一个变量。
6. 用失败测试锁定根因，实施最小修复，再验证原症状和相关回归。
7. 若当前工作项已登记状态账本，调试期间保持或退回 `待实现`；修复完成且当前环境可运行的自动验证通过、只剩外部或人工验证时改为 `待验证`。具体规则见 [状态账本规范](../references/status-ledger.md)。

## 快速路径

1. 捕获准确失败命令或行为。
2. 查看被点名的责任位置和近期相关变更。
3. 陈述一个假设及其证据。
4. 添加或更新最聚焦的回归测试。
5. 做一次修复并重新运行目标验证。

## 完整路径

跨组件、性能或难复现问题应在每个边界增加诊断信息，记录输入、输出、状态和耗时，并逆向追踪到最早产生错误的位置。连续三次修复尝试失败后，停止打补丁，重新检查假设和架构。

## 红旗

- “先试试这个改动”。
- 一次提交多个无法独立验证的修复。
- 没有复现就断言根因。
- 只修复报错位置，不追踪错误数据的来源。
- 三次失败后继续第四次同类尝试。
