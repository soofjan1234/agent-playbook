# 错误案例：同步失败重试设计

这是写作反例，业务设定用于演示，不代表任何项目的现状或已批准方案。与[正确案例](design-good.md)的业务约束相同；问题在内容取舍与组织，不在重试规则。

## 待改写正文

### 1. 背景与建设目标

目前用户手动同步文件，遇到临时网络故障后需要重新点击同步。为了提升同步体验，需要增强系统在临时网络故障下的恢复能力，减少用户重复操作。因此，本次设计引入失败重试机制，在网络恢复后自动再次尝试，避免每次都需要用户手动重试。

本方案的目标是提高同步过程的可靠性，同时兼顾可控性和可维护性。通过自动重试减少人工干预，通过失败上限避免无限重试，通过取消能力保证用户可以主动结束任务。

### 2. 范围与边界

本次仅覆盖单进程内、由用户手动发起的同步任务，继续调用现有同步逻辑，不修改 HTTP 接口，也不持久化重试状态。不涉及多进程协调和进程重启后的任务恢复。

也就是说，这次只增加已有同步任务失败后的重试能力，不引入新的同步入口。由于状态保存在内存中，进程退出后不会保留等待重试的任务。

### 3. 组件与状态设计

重试逻辑负责失败分类、重试等待和次数控制，同步逻辑负责执行一次文件同步。取消逻辑负责停止后续重试，日志逻辑负责记录任务执行结果，各部分职责需要明确。

同一任务最多执行四次，包含首次执行和三次重试。任务成功后结束；参数错误直接失败；临时网络故障包括超时和服务暂不可用，可进入等待重试。用户请求取消后，任务最终记为“已取消”。

### 4. 重试策略

首次失败后等待 5 秒，第二次失败后等待 10 秒，第三次失败后等待 20 秒。等待从上一次执行失败时开始计算，第四次仍失败就结束任务。

采用有限次数重试，是为了让短暂网络故障有机会恢复，同时避免服务长期不可用时一直请求。随着失败次数增加逐步延长等待，也能降低连续请求的频率。

对于超时或服务暂不可用，应按照上述等待策略继续尝试。对于参数错误，不应采用上述重试策略。只要某次执行成功，就不需要继续执行剩余重试。

### 5. 取消与并发控制

同一任务的两次执行不能重叠。如果任务正在等待，取消后立即结束等待；如果一次同步正在执行，则让它完成或按现有超时退出，然后结束任务，不再重试。已同步的文件不回滚，最终状态为“已取消”。

取消的含义是阻止后续重试，不是撤销已完成的文件同步。正常完成的任务不再重试，取消的任务也不再重试。任何等待和重试都需要遵守同一任务不能同时执行两次的原则。

### 6. 日志与生命周期

每次执行结束后，记录任务标识、执行次数和结果，失败时附带原因。等待期间不逐次输出日志。

重试状态仅在内存中保存，不写入持久化存储。因此，进程退出后等待中的任务不会在重启时恢复。本方案不会新增重启恢复机制。

### 7. 实施安排

先增加失败分类，再增加重试计数和等待逻辑，然后接入取消处理。随后检查并发控制，补充结果日志，最后验证重试次数、取消行为和进程退出场景。

### 8. 验证标准

| 场景 | 预期 |
| --- | --- |
| 临时网络故障 | 从每次失败时起，依次等待 5、10、20 秒；累计执行不超过四次 |
| 同步成功或参数错误 | 任务结束，不再重试 |
| 等待中取消 | 取消后结束等待，不再调用同步逻辑 |
| 执行中取消 | 当前执行完成或超时后记为“已取消”；不重试、不回滚已同步文件 |
| 同一任务连续失败 | 不出现两次执行重叠；结果日志包含任务标识、次数和失败原因 |
| 进程退出后重启 | 不恢复退出前等待的任务 |

### 9. 总结

通过上述设计，可以在保留现有同步方式的基础上，建立有次数限制、支持取消且可记录结果的重试机制，实现可靠、可控的失败恢复。
