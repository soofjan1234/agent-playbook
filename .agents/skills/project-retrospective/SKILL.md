# 项目复盘沉淀

## 目标

把已经发生的项目问题、用户纠正或高成本路径，转化为当前仓库可发现、可维护的最小知识。重点是防止项目内复发，不把局部经验误写成全局规则。

## 输入与边界

1. 优先使用当前任务已有的对话、命令、错误和制品证据；证据足够时不要重新进行宽泛搜索。
2. 先确认目标仓库和适用目录。无法确定项目边界时只输出候选，不写入文件。
3. 区分事实、推断和用户明确纠正。用户纠正是当前沉淀的约束，但仍要避免扩展到无证据的项目或场景。
4. 调用本 skill 不代表允许任意修改。写入前先给出目标、范围、文件、内容摘要和验证标准；当前线程已经明确批准这些内容时不重复询问。
5. 不处理普适性经验。跨项目都成立的规则应交给全局 `AGENTS.md` 或全局 skill，不写入当前仓库。

## 沉淀选择

选择能让 Agent 在正确时机看到、同时占用最少上下文的载体：

| 经验性质 | 默认载体 |
| --- | --- |
| 每次相关任务都不能遗漏的稳定规则 | 适用范围内最近的 `AGENTS.md` |
| 当前仓库内可重复执行的多步流程 | `.agents/skills/<name>/SKILL.md` |
| 仅在特定故障或模式下需要的详细说明 | 项目 skill 的 `references/` |
| 设计、实验过程、历史证据或交接材料 | `docs/my-skills/` 下的既有分类 |
| 经常变化的 IP、版本、路径或设备状态 | 项目配置、设备清单或其他事实源；规则只指向事实源 |
| 一次性事件且不能改变后续决策 | 不沉淀 |

普通文档不会仅因存在就被 Agent 主动读取。若后续任务必须发现该文档，应由适用的 `AGENTS.md` 或项目 skill 提供简短触发条件和链接。

## 工作流

1. **提炼教训：** 说明发生了什么、哪些工作必要、哪些成本可避免，以及最早可以采用的更短路径。
2. **限定范围：** 写清适用仓库、目录、任务类型和不适用场景；判断信息是稳定规则还是动态事实。
3. **检查既有沉淀：** 精确检查候选目标及其直接引用，优先更新已有规则，避免创建含义重叠的文件或 skill。
4. **提出最小方案：** 只保留会改变 Agent 后续决策的内容，并列出明确的拟修改文件和验证方法。
5. **等待批准：** 新增流程、修改 skill、接口或项目规则时，获得用户明确确认后再写入。
6. **实施沉淀：**
   - `AGENTS.md` 使用一句话或短 bullet，写行为和安全路径，不写复盘叙事。
   - 项目 skill 使用准确的触发描述，只包含当前仓库需要的流程；条件性细节再放入 `references/`。
   - 项目文档保留必要证据，并遵守仓库已有的状态账本或文档约定。
   - 动态事实写入项目认可的事实源，不把暂时值伪装成永久规则。
7. **验证发现与边界：** 确认目标位于正确作用域、没有重复规则、链接可达；创建或修改 skill 时运行可用的 skill 校验器，并检查描述能命中目标请求且不会吸引无关任务。

## 提案格式

```text
项目教训：
- ...

适用范围：
- ...

沉淀选择：
- 载体：...
- 原因：...

不沉淀：
- ...

拟修改：
- ...

验证：
- ...
```

## 红旗

- 因为一次失败就创建面向所有仓库的规则。
- 把完整复盘、日志或聊天记录塞进 `AGENTS.md`。
- 为单条事实创建多步骤 skill，或为多步骤流程只留一句模糊提醒。
- 把容易变化的地址、版本或状态写成永久事实且没有来源。
- 新建文档后没有任何触发入口，却声称 Agent 后续会自动看到。
- 未经批准修改目标仓库，或顺手整理无关规则。
