# 需求与设计

查清现状，先对齐总体设计，再按需补齐技术方案，确定做什么、怎样运行和如何验证。

<HARD-GATE>
目标、范围、关键技术方案和验证标准未呈现且未获用户确认前，不得进入实施计划或实现。总体设计确认后，未确定的技术方案仍在本阶段补齐；已有确认继续有效，只确认实质新增或改变的决定。
</HARD-GATE>

创建或实质修改 Markdown 文档时，必须同时使用 [md-work](../md-work/SKILL.md)。文档组织遵循[文档管理规则](../references/documentation-policy.md)。

## 核心流程

1. 读取最相关的当前实现、已有设计和项目约定，区分已验证事实、假设和用户决定。
2. 明确目标、范围、非目标、分工、主要流程和验收标准，形成简洁的总体设计并确认；已有结论直接复用。
3. 总体设计确认后，核对当前实现，找出影响开发的技术缺口；按需读取[设计检查](references/design-checks.md)，不强制为调查另建文档。
4. 存在多个关联技术问题时，先在同主题根目录创建或更新 `tmp-discuss.md`，集中列出问题、推荐方案、必要理由、待验证内容及用户意见和确认状态，供用户批量审阅；简单任务可直接在对话中讨论，不强制创建工作稿。具体规则见[文档管理规则](../references/documentation-policy.md#集中讨论稿)。
5. 先讨论组件交互、状态归属和关键运行流程，再按依赖细化接口、数据、鉴权与失败恢复。用户可批量确认、逐项批注或暂缓；只继续讨论分歧和遗漏，不重复确认已定事项。工作稿可先写供审阅，正式设计须待用户明确确认写入后，才整理进 `architecture/`；总体范围变化时再更新 `design.md`。不固定 API 与数据库等专项的先后顺序，也不强制每类问题独立成文。
6. 检查本次实施所需的关键技术决定已写明、可供无聊天上下文的执行者使用，记录已确认范围和未决项并同步状态。不能仅凭总体设计获批就跳过必要技术设计。
7. 多步骤任务交给 plan-work，明确的小改按项目约定进入 build-work；只推进技术前提已确定的范围，不把关键选择留给计划或实现猜测。

## 讨论与确认

- 根据任务选择讨论深度。范围、方案和验证已经明确时，一次简短讨论即可；缺少哪些决定就补哪些，不规定访谈轮数。
- 目标、范围仍不明确时，先澄清这些问题，再细化技术方案。用户只要求澄清需求时保留范围说明，不自动扩展任务或视为技术设计已获批准。
- 影响成本、范围或长期维护的选择，比较有实质差异的方案并给出推荐；用户已经确定的方向不重新比选。
- 方案涉及超时、取消、并发或恢复时，说清具体触发条件、谁采取什么动作、最终保留什么状态；检查项按相关性使用，不逐项扩写章节。
- 大致交付阶段按可交付能力划分；逐文件步骤、代码顺序和测试命令留给 plan-work。
- 下游发现关键假设失效或缺少决定时，回到本 skill 更新受影响部分，保留其余已确认内容。

## 已确认内容落盘

- 已确认的聊天与讨论稿结论是正式设计的正文来源；用户明确授权正式落盘后，只整理格式、链接和必要上下文，不另起模板重写方案。讨论稿及讨论确认本身不自动授权修改正式设计。
- 保留原决定、数值、条件、失败行为和验收要求；缺少会改变实现的关键内容时先补充讨论，不在落盘时自行决定。
- `design.md` 保持简洁；精简时将需要展开的技术决定移入或合并到已有 `architecture/` 专项，不得删除决定或只留在聊天中。
- 用户指定路径时遵循指定路径；已有相关设计时更新原文。默认设计目录、编号和文件名遵循[文档管理规则](../references/documentation-policy.md)。
- 持久化实际设计时，按[状态账本规范](../references/status-ledger.md)更新主题设计表；仅有范围说明时更新主题入口，不虚构设计批准或计划记录。
- 已有正式落盘授权继续有效，不重复询问；出现实质变更才对变更部分补充确认。不得把讨论稿写入权限当成正式设计写入权限。设计确认不代表实现或验收完成。

## 自检

- 能否直接看懂目标、范围、改后怎样运行以及如何验证？
- 是否把关键失败处理或技术决定留给计划、实现阶段猜测？
- 总体设计是否简洁且能找到相关专项；本次实施依赖的技术方案是否已记录并确认？
- 是否重复提问、重复审批，或重新维护另一套范围和验收标准？
- 是否支持批量审阅并保留未决项；是否未经正式落盘授权就修改了设计？
- 是否为了模板完整而增加无关章节、文档或方案？
