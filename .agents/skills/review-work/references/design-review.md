# 设计评审

判断设计能否在真实约束下达成目标，而不是只检查文档章节是否齐全。先读取相关代码、现有行为、规范和历史决策；无法验证的前提必须显式标注。

## 前置条件

1. 明确问题、目标、非目标、范围、约束和成功标准。
2. 区分当前事实、设计假设、用户决策和仍待确认的问题。
3. 若目标、范围或验收尚未形成，指出需要退回 shape-work；若系统实现的关键决策尚未形成，指出需要退回 design-work，不替用户暗中补全选择。

## 评审维度

1. **目标与范围**：设计是否解决真实问题，非目标和责任边界是否清楚，是否发生范围漂移。
2. **事实与假设**：关键判断是否有代码、数据、文档或实验依据；假设失效时会造成什么影响。
3. **方案与取舍**：是否考虑实质不同的替代方案，推荐理由是否匹配约束，是否存在更小的可行方案。
4. **边界与数据流**：模块所有权、输入输出、状态转换、依赖方向和故障传播是否明确。
5. **契约与正确性**：接口、数据格式、错误语义、幂等、并发、权限、安全和一致性约束是否足够。
6. **兼容与演进**：升级、迁移、降级、回滚、旧版本兼容和数据恢复是否可行。
7. **观测与验证**：成功与失败是否可观察，验收标准能否证明目标，是否覆盖关键边界和失败路径。
8. **成本与风险**：复杂度、性能、资源、运维和发布风险是否被识别，缓解措施是否与风险相称。

## 简化与优化检查

- 能否缩小首个纵向切片，同时保留完整输入、处理、输出和验证闭环。
- 是否重复维护同一事实、状态或契约，能否建立单一来源。
- 是否为了未确认的未来需求提前引入抽象、扩展点、组件或状态。
- 是否能减少跨模块写入、隐式耦合、同步步骤或故障面。
- 优化建议是否有明确瓶颈或收益证据；未经测量的性能猜测不得提升为阻断项。

## 设计评审红旗

- 文档结构完整，但关键事实未经调查或与当前实现冲突。
- 只描述正常流程，没有错误、边界、兼容、回滚或验证路径。
- 只给单一方案，却没有说明约束为何排除其他方案。
- 把实施细节堆积当作设计充分，或用未来扩展性掩盖当前过度设计。
- 验收标准只能证明“做了”，不能证明目标已达成。
