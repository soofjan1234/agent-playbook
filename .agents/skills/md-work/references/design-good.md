# 正确案例：同步失败重试设计

这是与[错误案例](design-bad.md)配套的写作示例，不代表任何项目的现状或已批准方案。两个版本的业务约束相同，以下展示精简后的正文。

## 方案

用户手动同步遇到临时网络故障时，系统自动重试，减少用户重新点击同步的次数。只处理单进程内的任务，复用现有同步逻辑；HTTP 接口不变，不处理多进程协调。

| 本次执行结果 | 后续动作 |
| --- | --- |
| 成功 | 结束任务 |
| 参数错误 | 直接失败，不重试 |
| 超时或服务暂不可用 | 从本次失败时起，按重试次数依次等待 5、10、20 秒后重试；最多执行四次，包含首次执行 |

有限次数和逐步延长的等待，让短暂故障有机会恢复，也避免服务长期不可用时持续密集请求。

同一任务的两次执行不能重叠。用户取消时，立即结束尚未完成的等待；正在执行的同步仍按现有逻辑完成或超时，然后将任务记为“已取消”。此后不重试，已同步的文件不回滚。

每次执行结束后记录任务标识、执行次数和结果，失败时附带原因；等待期间不逐次输出日志。重试状态只保存在内存中，进程退出后丢失，重启不恢复。

## 验收

- 连续注入临时网络故障：每次失败后分别等待 5、10、20 秒，总共执行四次；无重叠执行，结果日志能定位任务、次数和失败原因。
- 某次成功或返回参数错误：观察不到后续同步调用。
- 分别在等待中和执行中取消：等待立即结束；进行中的执行完成或超时后，最终状态为“已取消”，没有后续重试，已同步文件仍保留。
- 在等待中退出进程并重启：原任务不再执行。
