# 代码变更评审

审查真实差异，而不是会话印象。先固定基准点、目标点、原始需求和仓库规范，再沿调用链验证行为。

## 评审步骤

1. 确认真正的 diff、未跟踪文件和评审范围，避免把基准外改动归入结论。
2. 分别检查需求符合性与工程质量，避免一个维度遮蔽另一个。
3. 当范围包含源代码时，对最小相关子目录运行 `fuck-u-code analyze <path> -l zh`；前后端分离时分别扫描。
4. 检查所有新增和修改源文件的行数，对超长文件执行职责与边界专项审查。
5. 检查新增和修改代码是否遵守 `build-work` 的中文注释规范。
6. 先按本次 diff 的风险信号选择适用维度，再根据风险运行最具体的测试、静态检查、构建或并发验证；环境缺口必须作为残余风险报告。

## 风险路由与六个维度

所有代码变更至少检查“需求与正确性”“设计与可维护性”“测试与验证”。安全、可靠性和性能按实际风险信号深入审查；未触发某维度不是问题，不得为了完整性制造建议。

| 风险信号 | 需要深入检查的维度 |
| --- | --- |
| 用户输入、权限、敏感数据、SQL、Shell/系统命令、浏览器身份态 | 安全与权限边界 |
| 共享状态、状态迁移、goroutine/异步任务、RPC/HTTP/消息队列、关键外部依赖 | 可靠性、错误处理与可观测性；必要时需求与正确性 |
| 数据库循环、批量数据、高频路径、缓存、文件/网络 IO、明确性能目标 | 性能与资源消耗 |
| 公共行为、状态分支、修复缺陷、异步或副作用变化 | 测试与验证 |

### 1. 需求与正确性

- 规格、接口契约和兼容行为是否完整实现，是否出现范围漂移。
- 边界条件、空值、错误返回、状态迁移、事务边界、幂等性和副作用顺序是否正确。
- 差异涉及共享状态或并发时，锁、所有权、取消和竞态是否保持不变量。

### 2. 安全与权限边界

- 仅在存在相应边界时检查鉴权、越权、敏感数据暴露，以及 SQL、Shell、模板/HTML 等注入风险。
- CSRF 只在浏览器 Cookie 身份态等适用场景检查；XSS 只在不可信内容进入渲染边界时检查。
- 报告安全问题必须指出输入来源、传播路径、危险操作或缺失的访问控制；不能把通用安全建议当缺陷。

### 3. 可靠性、错误处理与可观测性

- 外部调用的超时、取消、错误传播、重试和回退是否符合业务目标；重试前先判断幂等性、重试预算和放大风险。
- 异步任务、消息和补偿路径在失败、重复或部分成功时是否可恢复或可人工处理。
- 关键失败是否具有足以定位问题的结构化日志、指标、追踪或审计信息，且不泄露敏感数据。
- 熔断、降级和 fallback 仅在依赖关键性、故障影响或服务目标证明需要时提出。

### 4. 设计与可维护性

- 职责、分层、接口边界、耦合和复用是否让改动可理解、可测试、可演进。
- 结合文件规模、职责数量、嵌套/认知复杂度、修改频率和热点判断是否需要拆分；函数或文件较长本身不构成问题。
- 重要常量、初始化逻辑、多步骤业务函数和核心算法是否有解释业务意图、约束或不变量的中文注释。

### 5. 性能与资源消耗

- 仅在风险信号触发时检查查询次数、N+1、索引、返回字段、内存分配、连接/文件句柄、缓存和网络/磁盘 IO。
- 性能发现必须给出调用频率、数据规模、执行计划、剖析/基准、资源上限或清晰调用链中的至少一种证据。
- `SELECT *`、循环、临时对象或未使用缓存本身不自动构成问题；只有可证明的负担、容量风险或约束冲突才报告。

### 6. 测试与验证

- 测试应证明公共可观察行为、异常路径、状态变化和关键副作用，而不只追求行覆盖率。
- 检查断言是否直接证明预期结果，是否过度模拟、遗漏边界，或让测试与真实契约脱节。
- 根据风险选择最具体的构建、静态检查、单元/集成/端到端测试和并发验证；未运行项必须写成验证缺口，不得视为通过。

## 质量与文件规模扫描

1. 对最小相关目录运行 `fuck-u-code analyze <path> -l zh`；大型仓库需要更多热点时使用 `-t <n>`，不要默认扫描无关目录。
2. 将总分、异常指标和热点文件作为风险地图，再回到真实差异和调用链验证；工具报告不能单独证明缺陷。
3. 工具不可用或执行失败时继续人工审查，并在结论中说明原因和缺失的质量证据。
4. 统计所有新增和修改源文件的总行数。默认超过 500 行时触发专项检查，但行数本身不构成问题。
5. 结合职责数量、嵌套和认知复杂度、修改频率、热点排名、相邻文件规模判断是否过长；新增超长文件从严审查。
6. 生成文件、第三方依赖、快照和纯数据文件不参与长度判断。
7. 发现超长文件问题时，指出应拆出的具体职责、边界和验证方式，不只写“文件太长”。

## 注释审查

1. 只审查本次新增或修改范围，不要求为无关旧代码批量补注释。
2. 检查重要常量和初始化逻辑是否说明业务含义与原因，具名函数和方法是否使用符合语言约定的中文文档注释。
3. 多步骤业务函数应使用独占一行的 `// 1.`、`// 2.`、`// 3.` 按执行顺序标注，且注释放在对应代码之前，不能写在代码行尾。
4. 复杂业务和核心算法应解释业务意图、关键不变量、边界条件或选型原因；简单代码不得用复述实现的注释制造噪音。
5. 仅当缺失、错误或过时注释会影响理解和维护时提出问题，并指出应补充的具体意图或约束。

## Go 并发验证

当差异涉及共享状态、锁、goroutine、客户端热切换或其他并发行为时，优先对最小相关包运行 `go test -race`，不要求无关审查默认执行全仓 race 检测。

Windows 下若 `CGO_ENABLED=0`，可在当前 PowerShell 命令会话临时启用：

```powershell
$env:CGO_ENABLED = '1'
go test -race ./相关包/...
```

`-race` 还需要当前平台支持且存在可用的 C 编译器。环境不满足时继续代码与同步关系审查，在结论中明确 race 检测未覆盖及原因；不得把环境失败视为代码测试失败。

## 代码评审红旗

- 没有基准点就声称审查了全部变化。
- 只检查风格，不检查规格、行为和调用链。
- 对每次改动机械运行全部六个维度，或为了完成清单制造无证据的建议。
- 用 `fuck-u-code` 分数代替对真实差异的审查。
- 仅凭超过行数阈值就要求拆分文件。
- 为简单代码缺少注释提出形式化问题，却遗漏复杂业务和核心算法的关键解释。
- 把静态检查、编译证明或环境失败误报为测试通过。
