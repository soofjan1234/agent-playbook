# 后端开发

使用这个 skill，让后端改动贴合现有代码库，而不是临场发明一套新风格。

## 工作流程

1. 先识别精确的后端改动面：路由、handler、service 函数、middleware、配置项、命令封装、模型或测试。
2. 优先用精确名称搜索：函数名、路由路径、事件名、配置 key、错误字符串或导出符号。
3. 编码前先阅读附近代码和同类实现。优先沿用现有 controller、service、util、test 模式，不轻易新增抽象。
4. 动手前把请求跨层链路想清楚：请求结构、参数校验、service 行为、错误处理、日志、响应格式和测试。
5. 做保持现有模块边界的最小改动。
6. 行为变化必须补充或更新聚焦的后端测试。
7. 先运行最具体有效的验证；若改动影响共享行为，再扩大验证范围。

## 代码规范

- 遵循现有命名、包结构、响应 helper、日志风格、错误包装和测试写法。
- 如果代码库已经使用 service 层，不要把业务逻辑堆进 controller。
- 能复用已有 Docker、配置、校验、鉴权、锁、缓存、文件系统 helper 时，优先复用。
- 核心逻辑和关键业务步骤必须写清晰的中文注释。注释应解释意图、约束或不明显的环境行为。
- 避免写只是复述单行代码的空注释。
- shell 命令、服务管理器、文件系统路径和 OS 相关行为都视为环境敏感点。新增命令执行前，先检查现有平台判断和保护逻辑。
- 保留用户在工作区中的改动，不要回滚无关文件。

## Go 验证

- 优先运行定向测试，例如 `go test ./api/service/... -run TestName`。
- 在 Windows/Codex 环境中运行 Go 测试时，优先把 `GOCACHE` 临时设置到工作区内。
- 如果后端改动影响共享契约、路由、middleware 或配置初始化，运行相关包测试或完整 `go test ./...`。
- 无法运行的验证必须说明原因。
