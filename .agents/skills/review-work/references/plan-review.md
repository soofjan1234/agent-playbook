# 计划评审

判断计划是否忠实落实已批准设计，并能由没有当前会话历史的执行者安全实施和验证。

## 前置条件

1. 找到已批准设计或足够具体的需求，核对版本、范围和仍未解决的决策。
2. 设计存在关键歧义、未验证技术选型或未批准行为时，将其列为上游阻断项，不用计划细节掩盖问题。
3. 映射相关文件、模块责任、公共契约和测试接缝，验证计划引用的路径、符号和命令真实存在或明确将被创建。

## 评审维度

1. **需求追溯**：每项目标、约束和验收标准是否映射到至少一个任务和验证证据。
2. **范围一致**：是否遗漏设计内容、加入未批准能力，或重复实现已有机制。
3. **纵向切片**：任务是否形成可独立验证的用户可观察行为，而不是按 controller、service、database 等技术层横切。
4. **依赖顺序**：契约、迁移、兼容层、实现、清理和发布的先后关系是否正确，是否存在循环或隐含前置条件。
5. **执行精度**：每项任务是否给出精确文件、符号、步骤、命令、预期结果和阻塞依赖。
6. **验证闭环**：是否冻结最小输入输出契约，并按 RED → 目标 GREEN → 最终相关全量安排验证；新增失败时才扩大相邻检查。
7. **迁移与发布**：数据迁移、灰度、回滚、旧版本共存、配置和外部依赖是否有安全步骤及停止条件。
8. **可交接性**：执行者无需聊天上下文即可判断做什么、为何这样做、何时完成以及失败后如何处理。

## 简化与优化检查

- 能否减少任务数量或合并重复步骤，同时保持每个切片可独立验证。
- 是否存在没有对应需求、风险或验证价值的预留任务。
- 能否提前验证高风险假设，避免完成大量低风险工作后才发现路线错误。
- 是否把同一契约、迁移或测试在多个任务中重复定义，导致执行时漂移。
- 是否能用更窄的目标测试和明确预期缩短反馈，但仍保留最终相关全量验证。

## 计划评审红旗

- 设计未批准就把猜测固化成实施任务。
- 一个任务同时横跨多个独立子系统，无法单独验证或安全回退。
- 用文件层级代替用户可观察的纵向行为。
- 使用 `TODO`、`TBD`、“适当处理”或“与上一步类似”等隐藏上下文。
- 计划只有动作，没有失败测试、目标测试、最终验证和预期结果。
- 文件、函数、类型或命令名称前后不一致，或者与仓库事实不符。
