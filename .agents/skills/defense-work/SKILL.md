# 防御工作流

仅当用户在已产出并确认的 `plan.md` 后手动调用 `$defense-work` 时使用。它把计划转成可验证的防御义务，并在实现后基于真实测试结果更新状态；不替代计划、代码审查或测试执行。

## 两个阶段

### 计划阶段：先列出必须防住什么

1. 读取已确认的 `plan.md`，以及其中明确引用的需求、契约或现有源码；范围不清楚时先询问，不从未确认的计划推断需求。
2. 按业务职责建立节点。每个节点用人话解释：解决什么问题、在哪个场景发生、系统怎样处理、成功及拒绝/失败时会看到什么结果、为什么这一步不可少。不要用函数、包、字段或调用顺序代替解释。
3. 每个节点额外编写可独立阅读的讲解材料：一句话结论、一个从前置状态到结果的具体业务例子、1～3 个易混淆术语的解释，以及一个最常见的错误理解。例子使用最小虚构角色和业务对象，例如“客户邮件 A、客服回复 B、管理员小王”；只能表达当前计划、实现或测试已经支持的行为，不得补造能力。
4. 从正常路径、拒绝/提前结束、恢复/重试、并发、边界和副作用推导应测场景，并说明触发条件与应观察结果。
5. 新地图中的每个场景默认标记 `○ 待验证`。计划存在或测试文件存在，都不是打勾的证据。
6. 节点一般在5-10个之间

### 实现后：只用真实运行结果更新

1. 重新读取当前实现和相关测试，先确认测试是否真的在当前任务中运行，或用户是否提供了可核验的运行结果。
2. 只有同时满足下列条件，场景才标 `✓ 已证明`：测试真实运行通过；关键断言直接证明该场景的预期可观察结果；测试与当前实现及该场景可可靠关联。
3. 相似路径被覆盖、但关键触发条件、状态变化或副作用没有被直接断言时，标 `△ 部分证明`，不得打勾。
4. 未运行、没有充分测试，或关联无法确认时，保持 `○ 待验证` 或标 `? 待确认`。不要从测试名称、旧报告或一般经验推断为已证明。

## 交付地图

生成可离线打开的 HTML 页面。未指定目录时，MVP 归档到 `docs/mvp/feature-defense/<范围>-map.html`；已交付版本、缺陷修复或变更归档到对应主题的 `docs/changes/YYYY-MM-DD-<主题>/feature-defense/<范围>-map.html`。已有旧目录不自动迁移。

创建或更新地图前，读取并复用 [HTML 模板](assets/feature-defense-map.html)，只替换页面元数据和业务节点数据，不另起一套布局或配色。模板中的演示节点必须全部替换，不能出现在交付物中。保持以下视觉不变量：

- 页面固定使用模板的浅色配色，不根据系统深色模式覆盖全局文字颜色。
- 颜色从模板变量复用；不要给浅色卡片搭配浅色文字，也不要用全局 `.status` 选择器影响页头。
- 顶部为渐变标题区；正文保留紧凑/展开流程、四格节点讲解和三列防御信息。
- 节点数量由实际业务职责决定，不为匹配示例强行凑固定数量。

页面保留上方可点击的功能导航，默认紧凑横向展示并支持展开/缩回。点击节点后只显示三个板块：

- **做了什么**：按“一句话结论 → 具体例子 → 关键术语 → 不要误解”展示计划或实现的业务解释，不展示实现标识符。
- **应测场景**：每项内联显示 `○ 待验证`、`✓ 已证明`、`△ 部分证明` 或 `? 待确认`。
- **可能漏掉什么**：只列尚未充分证明场景的具体风险与后果。

异常、拒绝和恢复必须归入“应测场景”或“可能漏掉什么”，不单列为板块。源码、测试名称、文件位置、断言和关联理由只保留为内部取证；页面不展示，也不提供展开入口。

详细字段与验收见 [页面契约](references/feature-test-map-contract.md)。每次生成或更新地图前都必须读取该文件。

## 节点讲解

当用户点名地图节点，例如“讲讲 A3 · 6”，先以页面中的展示步骤和标题精确定位节点，再重读该节点关联的当前计划、源码或测试证据。按“结论 → 具体例子 → 关键术语 → 不要误解”讲解：

1. 先用一句话说清该节点在整个业务链路中的作用。
2. 用一个最小例子展示谁带着什么状态进入、经过什么业务动作、最后能观察到什么结果。
3. 只解释当前例子需要的术语；出现多个版本、状态或标识时，先区分它们的对象和用途。
4. 明确该节点不做什么，特别是“候选不等于发布”“检索候选不等于可靠依据”这类状态边界。

不要只复述地图的短标题、源码函数名或测试名称；也不要因用户追问而把未实现能力描述成已经可用。

## 完成前检查

- 计划阶段的所有场景均为 `○ 待验证`，除非本次也有满足条件的真实测试运行证据。
- 每个 `✓ 已证明` 都能回溯到真实运行的测试及直接断言；否则降级为 `△ 部分证明`、`○ 待验证` 或 `? 待确认`。
- 页面仅有三个信息板块，且每个节点可通过键盘或点击切换；窄屏可纵向阅读。
- 每个节点的“做了什么”都含一句结论、具体例子、必要术语与防误解句；例子与当前节点的状态边界一致。
- 实际渲染检查浅色页面的页头、节点选中态、四格讲解、三列防御信息、展开/缩回和窄屏布局；不能用 HTML 或 JavaScript 语法检查代替视觉检查。
- 主要正文、次要文字、状态、强调标题和警示标题与其背景的对比度均不低于 `4.5:1`。若环境无法打开本地页面，明确说明视觉检查未完成，不得声称页面样式已通过。
- 如实说明计划范围、实际运行的命令和未证明项；不要声称运行过未实际执行的测试。
