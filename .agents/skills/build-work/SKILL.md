# 实现与验证

按明确需求或计划，以最短反馈循环交付可验证的纵向行为。

## 核心关卡

1. 先完整理解已确认范围、系统设计或计划；范围与验收歧义退回 shape-work，架构与契约歧义退回 design-work，执行步骤歧义退回 plan-work。
2. 检查分支和工作区是否安全；需要隔离时优先使用平台原生能力，再考虑 Git worktree。
3. 对明确输入输出的阶段实现，先冻结最小契约，按 `AGENTS.md` 执行 RED → 目标 GREEN → 最终相关全量；功能和缺陷用真实行为验证，纯说明修改检查内容、差异和链接。
4. 按变更影响执行目标验证及必要类型检查；最终运行相关完整验证，不在产物未变化时机械重复。
5. 只有任务独立、不会修改相同状态时才并行；否则按依赖顺序执行。
6. 若当前计划已登记主题计划表，实现期间保持 `待实现`；实现完成且当前环境可运行的自动验证通过、只剩外部或人工验证时改为 `待验证`。具体规则见 [状态账本规范](../references/status-ledger.md)。

## 实现循环

1. 选择最小用户可观察行为，明确输入、输出、通过条件和受影响范围。
2. 选择能证明预期的验证。新增或修复行为优先使用能复现问题的回归测试；现有用例已覆盖时复用，不为形式新增用例。
3. 对适用 RED 的阶段实现先确认失败及其原因；用例直接通过时核对覆盖是否充分，不为凑失败而破坏测试。纯说明修改使用内容和差异检查。
4. 在获批范围内做最小实现，运行目标验证；只有新失败或跨组件风险才增加相邻验证。
5. 必要时在目标验证通过的前提下重构，改动后重跑受影响检查；完成时执行最终相关全量验证。

实现中发现契约变化或新的长期限制时，先处理必要的设计确认，再更新对应权威正文。文档写回遵循 [文档管理规则](../references/documentation-policy.md)，不把变更历史复制成第二份当前说明。

## 验证策略

明确输入输出的阶段实现默认遵循 `AGENTS.md` 的 RED → 目标 GREEN → 最终相关全量；选择端到端验证不自动豁免 RED。其他改动按风险和现有覆盖选择最短有效反馈：

- **Bug、复杂业务规则、关键不变量**：优先用失败复现或聚焦的回归测试锁定预期，再做最小实现；权限、计费、状态转换、幂等和并发边界不能只靠正常路径证明正确。
- **成熟模式、接线、行为保持型重构、已有充分覆盖的改动**：优先复用能证明契约的现有测试，必要时补集成或端到端验证，不机械要求每个函数新增单元测试。省略新增用例或不采用先失败后实现时，说明已有覆盖及选择依据，不覆盖项目或用户明确要求的验证顺序。
- **UI、环境和部署链路**：优先实际运行、交互或端到端验证；复杂局部逻辑仍按风险补充聚焦测试。

验证预期来自已确认的业务契约，不从当前实现或系统实际返回值反推正确答案。断言应在实现违反契约时失败；不要用重复实现、无有效断言或过度 mock 的测试充当证据。测试难写时先判断验证层次与边界是否合适，不为方便测试而无依据地新增抽象。

## 中文注释规范

以下规则只约束本次新增或修改的代码，不为补注释而批量改动无关旧代码：

- 为具有业务含义、单位、边界、协议值或不直观用途的常量定义添加中文注释；语义已经由名称完整表达的普通常量不强制注释。
- 为存在依赖关系、执行顺序、默认值、降级行为或环境约束的初始化逻辑添加中文注释，说明为什么这样初始化。
- 函数或方法有不直观的职责、约束或副作用时，用中文文档注释说明；项目或语言要求文档注释时遵循其格式，不强制给直观 getter、setter 添加重复解释。
- 多步骤业务函数按需要解释关键步骤；使用步骤编号时遵循项目和语言样式，顺序与执行一致，注释放在对应代码之前。
- 为复杂业务逻辑和核心算法说明业务意图、关键不变量、边界条件或选型原因；不要逐行翻译代码。
- 简单赋值、直观判断、普通调用、getter、setter 等语义明确的代码不添加无意义注释。
- 注释与代码同步更新；注释重点解释用途和原因，不重复变量名、函数名或语句表面含义。

## 执行模式

- **单 agent**：小型任务或共享状态较多。
- **顺序子任务**：计划包含多个相对独立切片；每项完成后审查再继续。
- **并行调查或实现**：仅限完全独立的问题域和文件范围，合并后统一验证。

使用子 agent 前遵守平台能力和用户授权，不为追求形式而拆分任务。

## 红旗

- 适用 RED 的阶段实现未确认有效失败原因就开始实现。
- 测试失败原因不明仍继续实现。
- 用大量 mock 验证实现细节。
- 多个 agent 同时编辑同一文件或共享状态。
- 目标测试通过后跳过受本次改动影响的构建、类型或相关回归验证。
- 为追求注释数量逐行复述代码，或给未修改旧代码做无关的批量注释改造。
- 将编号步骤写在代码行尾，或让编号顺序与实际执行顺序不一致。
