# 对齐需求与范围

通过有针对性的追问，让人和 AI 对项目要解决的问题、交付范围和成功条件形成同一理解。

<HARD-GATE>
需要澄清的需求范围和整体验收标准，须呈现并获得用户确认后再进入下游。已有确认仍适用时直接复用；仅对会改变范围或验收的缺口重新确认，遵循 `AGENTS.md`。
</HARD-GATE>

## 核心关卡

1. 先读取最相关的项目事实、现有行为、文档入口和约定；文档组织遵循 [文档管理规则](../references/documentation-policy.md)。
2. 明确要解决的问题、目标用户或使用场景、做什么、不做什么、约束和整体验收标准。
3. 将交付内容划成少量业务阶段，只说明每阶段交付的能力和依赖，不讨论文件与代码步骤。
4. 事实自行调查；把同一轮能回答的关键问题分组列出，让用户集中回答，再根据答案进入下一轮。
5. 用简短范围说明复述双方共识，明确未决定项，并等待用户确认。

## 需求访谈方式

用户可能只给出“帮我做 XXX”这样的初始请求。此时先根据已有上下文列出一组真正影响范围和验收的问题，不要求用户预先写完整需求。

- 每轮集中提出一组相关问题，优先覆盖目标用户、使用场景、核心结果、范围边界、硬约束和验收方式。
- 问题应便于集中回答；能给出合理选项时提供选项和推荐项，也允许用户直接补充自己的答案。
- 收到回答后，先归纳已经确认的内容和仍有影响的缺口，再提出下一组补充问题，避免重复询问。
- 通常在 3～5 轮内完成需求对齐。信息已足够时立即停止追问；经过 5 轮仍有关键分歧时，列出剩余决定及其影响，请用户选择是否继续讨论或暂按明确假设推进。
- 不为凑轮数提问，也不把能从仓库、现有文档或工具直接查到的事实交给用户回答。

## 职责边界

- 本阶段讨论“做什么”和“何时算成功”，不决定组件架构、数据库字段、状态机、协议、接口字段或具体文件修改。
- 可以调查现有实现和基本可行性，用于发现约束和避免提出无法落地的范围；调查结果不自动成为系统设计。
- 需求阶段的大致阶段按可交付能力划分。技术依赖、代码顺序和测试命令留给系统设计与实施计划。
- 如果已有明确且仍适用的范围、非目标和整体验收标准，简要复述后直接进入需要的下一阶段；尚未批准且任务要求设计确认时，再集中确认，避免重复访谈。
- 小型局部任务可以在一次简短讨论中同时说明范围、方案与验证，但必须清楚区分这三类结论。

用户明确要求 `design.md`、架构、数据模型、状态流、接口契约或技术选型时，应进入 design-work，不要让 shape-work 暗中代替它完成设计批准。

## 输出

范围说明保持短而可改，通常包含：

- 背景和要解决的问题。
- 目标用户或使用场景。
- 目标、范围和非目标。
- 已知约束、风险与待确认问题。
- 大致交付阶段及每阶段能力。
- 可观察、可判定的整体验收标准。

用户指定路径时写入该路径；项目已有相关范围正文时更新原文，不创建平行文件。MVP 优先使用 `docs/mvp/README.md`，后续变更优先使用同一主题目录的 `README.md` 或项目既有位置。需要持久化且项目沿用状态账本时，按 [状态账本规范](../references/status-ledger.md) 更新主题说明；只有实际设计或计划文档才登记对应表，不为范围说明虚构计划行。

## 快速路径

适用于一级任务：

1. 只读取最窄的相关事实。
2. 用一轮精简问题确认真正影响结果的缺口；问题可以有多个，但应能让用户一次集中回答。
3. 简述问题、范围、非目标和验收标准。
4. 只有仍缺少必要确认时才询问范围是否符合预期；已有有效确认时继续。

不要创建正式规格或计划。

## 完整路径

适用于二至三级任务：

1. 探索现有产品行为、用户路径、相关约定和历史范围决定。
2. 第一轮列出一组基础问题，确认目标用户、核心场景、期望结果、明确范围和硬约束。
3. 根据回答归纳共识，后续每轮只补充仍会改变范围、阶段或验收的关联问题；通常在 3～5 轮内收敛。
4. 对有实质差异的范围方案比较用户价值、成本、风险和交付顺序，并给出推荐项。
5. 创建或更新范围说明，优先修改已有主题入口。
6. 用用户可观察的行为呈现大致阶段和整体验收标准，标出仍待系统设计验证的假设。
7. 获得确认后进入 design-work。

## 红旗

- 以“需求很简单”为由跳过范围或成功标准。
- 在范围确认前开始系统设计或实现。
- 询问能从仓库直接找到的事实。
- 一次只问一个小问题，导致访谈被拉成长串零碎对话。
- 第一轮罗列大量互不相关的问题，或用户已经回答后重复询问。
- 把架构、数据库字段或接口参数混入需求范围并要求用户一并批准。
- 追问没有影响实现、验证或取舍的细节。
- 用技术任务列表代替可交付的业务阶段。
- 将阶段测试方法当成整体验收标准，或在下游重新维护另一套验收标准。
