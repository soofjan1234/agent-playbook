# 文档管理规则

## 写作原则

所有阶段的文档优先让读者容易理解和使用：先说重点，使用常用词和短句，减少术语、抽象表达和冗长措辞；必要术语首次出现时简要解释。根据读者和用途安排内容，不强求统一格式；简化表达时保留关键条件、约束和判断依据。

从第一次落盘起，就按读者需要做的判断或动作组织内容，不先堆全量信息再压缩。设计直接呈现方案、边界和验收；计划直接呈现执行顺序、验证方法和完成条件。每段只回答一个问题；已选定的方案保留结论、关键理由和仍有效的限制，不重复完整比选过程。精简不能省略数值限制、错误语义、兼容边界或验收标准，也不以字数为目标。

## 基本原则

- 每份正文回答一个主要问题。总体设计串起系统全貌，API、数据等专项文档承载各自细节。
- 开头先写结论和适用范围；使用具体行为解释术语，删除重复背景、空泛总结和无关扩展。
- 同一事实只在一个权威正文维护，其他位置写摘要和链接。拆出的文档必须能从上级入口找到。
- 按阅读目的和独立维护需要拆分，不按固定行数拆分；没有独立内容时不创建空文件。

## 工作阶段与产物

| 阶段 | 回答的问题 | 主要内容 |
| --- | --- | --- |
| 需求与设计 | 为什么做、做什么、怎样运行、何时算成功 | 目标、范围、非目标、约束、关键方案和验收标准；技术细节按需补充 |
| 实施计划 | 具体如何执行和验证 | 修改文件、关键函数、执行顺序、测试方法和通过条件 |

同一主题按“总体设计确认 → 调查技术缺口 → 按需通过 tmp-discuss.md 集中讨论 → 明确确认后写入技术专项 → 实施计划 → 开发验证”推进，总体和技术设计均属于 shape-work。小型明确任务可合并步骤，不为流程完整增加文档。正式落盘须有用户明确授权，已有授权不重复询问；总体设计获批不代表尚未讨论的技术方案获批。下游材料引用原设计，不重新维护范围和验收标准；本次实施依赖的关键决定必须先写明并确认，不能留给计划暗中决定。

## 文档组织

- MVP 资料放在同一入口下。总体设计、API 设计、数据设计和计划按需要拆分。
- 小计划保留一份；复杂计划按可独立验证的交付阶段拆成总计划和子计划。
- 后续功能和复杂修复按主题保存在 `changes/YYYY-MM-DD-<主题>/`；日期是主题首次创建日，后续更新复用同一目录，不因跨月新建平行主题。版本文档只汇总主题及整体验收，不复制设计与计划。
- 简单修复可在已有 Issue、提交或工作记录中保留原因、修复和验证，不强制创建完整文档组。

## 集中讨论稿

- 总体设计确认后，有多个关联技术问题需要用户审阅时，在同主题根目录维护一份 `tmp-discuss.md`。它是供批注的临时工作稿，可先写入，不是正式设计或实施计划；简单任务不强制创建。
- 每项写清问题、推荐方案、必要理由和待验证内容，预留用户意见及确认状态，不机械套用完整设计模板。区分建议、用户已确认、待验证和暂缓；用户未回复不视为同意，已有明确结论直接沿用。
- 集中提供一批相关问题供用户批量确认或逐项批注，后续只追问分歧和遗漏。允许暂缓不影响当前范围的事项，不把每项问题拆成一轮确认。
- 未经用户明确确认正式写入，不将工作稿建议写进 `design.md` 或 `architecture/`，也不把讨论稿登记为已批准设计。获得授权后，将结论整理到相关正式文档并同步 `status.md`；总体范围变化时才更新 `design.md`，避免重复维护同一规则。
- 正式文档完整承接必要结论、确认没有遗漏或仍需保留的未决与待验证内容后，再清理工作稿；只整理部分结论时继续保留。讨论稿不作为长期并行方案维护，也不能代替进入实施计划前的正式设计检查。

## 设计文档落盘

- 已有相关设计时更新原文，不新建平行方案。总体设计保持最简，讲清目标、范围、分工、主要流程、关键决定和验收；需要展开的技术细节统一放入同主题的 `architecture/`，并从总体设计链接。
- MVP 优先使用 `docs/mvp/design.md`；后续变更的首次综合设计默认放在 `docs/changes/YYYY-MM-DD-<主题>/design.md`，后续讨论持续更新原文。
- `architecture/` 可承载组件与部署架构、API／通信协议、数据与存储、状态归属与运行恢复、鉴权与权限等技术方案。这些是按需覆盖的问题，不是必建文件清单；关联内容可合写，已有专项优先更新，不创建空目录或占位文件。
- `architecture/` 中新增专项设计使用 `i.xxx.md`，编号取同目录最大值加 1，例如 `1.api-contract.md`。更新旧文档保留原名，不重排；历史 `design/`、`designs/` 等目录不在无关任务中自动迁移，新专项统一放入 `architecture/`，并维护总体入口链接。用户明确要求迁移时再连同引用一起调整。
- 精简 `design.md` 时，重复和无关表述可以删除；实现必需的技术决定必须保留在原文或转入专项，不能仅保留于聊天。专项按技术依赖逐步细化，不强制先 API 后数据库；总体和专项各自维护权威内容，避免复制。
- 用户说“写到 design.md”时默认保存为主题根目录的 `design.md`，不转换为编号文件；用户明确指定其他路径时遵循指定路径。只有关键长期取舍才单独建立 ADR，并从设计引用。
- 新建或更新实际设计后同步主题设计表；仅有范围说明时更新主题入口，不虚构技术设计已经批准。

## 收尾

- 最终结果与中间产物的合并、清理和证据保留按 [finish-work](../finish-work/SKILL.md#文档与临时产物收尾) 执行。
- 将已交付行为同步到当前架构、API、数据或操作说明；变更材料保留原因、方案和验证证据。
- 明确区分已批准、代码已实现、本地验证和目标环境验收。
- 每个主题的进度集中在一个 `status.md`，分为设计表和计划表，表内使用文档名而非链接；字段见 [状态账本规范](status-ledger.md)。MVP 与每个带日期的 changes 主题分别维护，顶层仅做导航；项目已有 Issue 或账本约定时优先遵循。
- 交接只写当前位置、阻塞、下一步和证据链接，不复制已有设计与计划。
